# 磕项目资料维护规章

本文件用于规范“磕【new】”项目资料的读取、写入、迁移和归档。项目指令只负责指向本文件；具体维护边界以本文件为准。

## 维护位置

项目静态资料以 GitHub 仓库 `laippmiles/ke-project` 的 `main` 分支为唯一日常维护源。二创资料直接位于仓库根目录下的分类目录中，不再放在 `磕/` 子目录。

原 Google Drive 和 ChatGPT Library 文件只作为迁移历史背景。除非用户明确要求回查旧版，不再把它们当作日常维护源，也不写回。

## 更新方式

讨论过程中不要立即提交。先记录待更新内容，等待用户明确表示“敲定”“归档”“提交”“按这个改”等确认。用户确认后，再更新静态资料。

一轮讨论敲定的结果应尽量合并为一个 commit。commit message 应简短说明本轮沉淀内容，例如 `更新项目资料维护规则`、`归档杀铃关系阶段设定`、`记录 Git 工作流`。

提交前必须检查变更边界：

- 二创世界观、人物、对白、正文资料写入根目录下对应的二创资料目录。
- 与二创无关的流程、工具、插件、故障排查、工作流结论写入 `chatRecord/`。
- 同步脚本和维护工具写入 `_system/`；普通写作资料不要放入 `_system/`。
- 私密、敏感、个人资料不得默认写入仓库。

提交后回读 commit 或文件内容，确认提交范围符合本轮讨论。只有验证成功的内容，才能报告为已更新。

发生版本冲突、目标文件不可读、目标文件不可写或保存失败时，停止处理该文件，保留原状，并在报告中说明失败项和原因。

## 隐私与敏感资料

本项目的资料维护范围是“磕”项目内的创作资料、原作材料、写作规则、设定讨论、稿件状态和与创作直接相关的索引。

与项目创作无关的个人生活、健康、用药、家庭、工作、账号、财务、联系人、现实身份信息，以及任何被文件名、目录、正文或用户说明标记为私密、个人、敏感、备忘、仅自己看的材料，不进入默认读取、迁移、归档或更新范围。

遇到这类材料时，只记录必要的最小状态，例如“发现但未纳入”“需要用户单独授权”，不要读取正文、摘录内容、写入 GitHub、合并进创作总集或在报告中展开细节。

只有用户对具体文件或具体类别单独明示批准后，才能处理相应私密或敏感资料。项目迁移、资料整理、定时归档、全量备份等宽泛授权，不自动覆盖这类材料。

## 覆盖范围说明

当前资料库保存的是可访问的项目静态资料，不等于旧项目完整聊天逐字原文已经全量迁移。后续报告中不能把“已迁移资料”说成“完整历史聊天已备份”。

整理聊天或补充资料时，应区分实际读取到的原文、摘要、检索线索、旧助手报告和用户记忆。只有有原文或可核验资料支持的内容，才能写入定稿资料。

## 报告要求

每次维护后，报告应说明实际读取和更新的范围、成功写入的 GitHub 文件、commit SHA 或链接、是否回读验证成功、未完成项、冲突项、需要用户补充的原文或授权。
