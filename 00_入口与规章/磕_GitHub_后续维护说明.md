# 磕项目资料后续维护说明

## 维护位置

以后维护“磕”项目静态资料时，以 GitHub 仓库 `laippmiles/ke-project` 的 `main` 分支为准。二创资料直接位于仓库根目录下的分类目录中，不再放在 `磕/` 子目录。

入口文件：`00_入口与规章/磕_GitHub_入口索引.md`。

原 Google Drive 和 ChatGPT Library 文件只作为迁移历史背景。除非用户明确要求回查旧版，不再作为日常读取或维护位置。

## 目录使用原则

- `00_入口与规章`：先读这里，确认入口、项目规章、资料维护规章和迁移清单。
- `01_核心总集`：长期写作圣经、人物理解、谈话总集和项目记忆包。
- `02_原作对白与校准`：原作对白、对白分析、分卷摘录、访谈和官方物料。
- `03_创作稿件`：正文、番外、梗概、场景大纲和交接稿。
- `04_提示词与外部工具`：RikkaHub、世界书、lorebook、模型注入稿。
- `05_素材附件`：PDF、图片、音频等非主文本素材。
- `90_旧版与待核对`：旧版、冲突副本、迁移原目录留存；不作为默认主体资料。
- `chatRecord`：与二创无关的流程、工具、插件、故障排查、工作流结论。
- `_system`：同步脚本和维护工具；普通写作任务不需要读取。

## 可直接写入项目 instruction 的文字

“磕【new】”项目的静态资料以 GitHub 仓库 `laippmiles/ke-project` 为准。主分支是 `main`。二创资料位于仓库根目录下的 `00_入口与规章`、`01_核心总集`、`02_原作对白与校准`、`03_创作稿件`、`04_提示词与外部工具`、`05_素材附件`、`90_旧版与待核对` 等目录中，不再进入 `磕/` 子目录。

每次需要读取或维护项目资料时，先打开 `00_入口与规章/磕_GitHub_入口索引.md`，再按索引进入具体文件。原 Google Drive 和 ChatGPT Library 文件只作为迁移历史背景；除非用户明确要求回查旧版，不再作为日常读取或维护位置。

长期写作规章以 `00_入口与规章/磕_项目规章_杀生丸与铃.md` 为准。涉及人物声音、称呼、关系阶段、资料调用和正式出文检查时，先读取该规章，再根据任务读取写作圣经、人物理解、对白集和对白分析。

资料读取、写入、迁移、归档和隐私边界以 `00_入口与规章/磕_资料维护规章.md` 为准。凡是与项目创作无关的个人生活、健康、用药、家庭、工作、账号、财务、联系人、现实身份信息，或被标记为私密、个人、敏感、备忘、仅自己看的材料，不进入默认读取、迁移、归档或更新范围；只有用户对具体文件或具体类别单独明示批准后，才能处理。

写小说正文、场景、对白、梗概、续写或最终润色前，先读取 `01_核心总集/磕_谈话总集_02_二创世界观与长线创作圣经.md`，并按任务需要读取相关场景、时间线、人物章节。

涉及人物关系判断时，同时读取 `01_核心总集/磕_谈话总集_01_杀铃关系研究与人物理解.md`。涉及杀生丸对白时，同时读取 `02_原作对白与校准/10_主体对白集/杀生丸前期对白_杀邪铃互动_原作对白集.md` 和 `02_原作对白与校准/20_对白分析与台词校准/杀生丸前期对白_杀邪铃互动_对白分析与二创校准.md`。`90_旧版与待核对` 中的旧版对白集只用于版本核对，不作为默认主体版。

讨论过程中不要立即提交。先记录待更新内容，等待用户明确表示“敲定”“归档”“提交”“按这个改”等确认。用户确认后，再更新静态资料，并尽量把同一轮讨论敲定的结果合并为一个 commit。提交后回读 commit 或文件内容，确认变更范围符合本轮讨论。

成稿后，回到写作圣经中的“连续性检查清单”和“正式出文自检”核对连续性、人物失真、称呼、模板化表达和设定冲突；修完再交付，不需要另行报告检查过程。

如果无法访问上述 GitHub 资料，必须明确说明缺失，不能凭记忆补设定或编造原作对白。

## 更新规则

1. GitHub 是唯一日常维护源，负责保存正式静态资料、提交历史和可回滚版本。
2. 一轮讨论敲定的结果尽量合并为一个 commit。
3. 与二创无关的流程、工具、插件、故障排查、工作流结论写入 `chatRecord/`。
4. 同步脚本和维护工具写入 `_system/`；普通写作资料不要放入 `_system/`。
5. 更新后必须回读 commit 或文件内容。只有验证成功的内容，才能报告为已更新。
