# 静态资料 Git 版本管理工作流

本文记录“磕”项目静态资料的长期维护方式。内容写成通用模型指令，不依赖某一个具体模型或产品；任何支持自定义 instructions、能访问 GitHub/Drive/本地文件的模型，都应按此执行。

## 资料源优先级

1. GitHub 仓库是静态资料的版本主库。
   - 仓库：`laippmiles/ke-project`
   - 主分支：`main`
   - 二创资料目录：`磕/`
   - 非二创讨论记录目录：`chatRecord/`
2. Google Drive 保留为模型读取入口、镜像和跨工具访问位置。
3. 原 ChatGPT Library 文件只作为迁移前备份。除非用户明确要求回查旧版或恢复，不作为日常维护源。

## 日常读取规则

1. 需要读取项目静态资料时，优先读取 GitHub 仓库中的对应文件。
2. 如果当前模型无法访问 GitHub，再读取 Google Drive 入口索引，并明确说明当前使用的是 Drive 镜像。
3. 如果 GitHub 与 Drive 内容不一致，以 GitHub 为准；除非用户明确指定要以 Drive 某个文件为准进行恢复或比对。
4. 无法访问指定资料时，必须明确说明缺失，不能凭记忆补设定，也不能编造原作对白或项目规则。

## 写入与提交规则

1. 讨论过程中不要立即提交。先记录待更新内容，等待用户明确表示“敲定”“归档”“提交”“按这个改”等确认。
2. 用户确认后，再更新静态资料。
3. 一轮讨论敲定的结果必须尽量合并为一个 commit。
4. commit message 应简短说明本轮沉淀内容，例如：
   - `更新项目资料维护规则`
   - `归档杀铃关系阶段设定`
   - `记录 GitHub 与 Drive 同步流程`
5. 提交前必须检查变更边界：
   - 二创世界观、人物、对白、正文资料写入 `磕/`。
   - 与二创无关的流程、工具、插件、故障排查、工作流结论写入 `chatRecord/`。
   - 私密、敏感、个人资料不得默认写入仓库。

## 多文件变更规则

1. 如果当前工具支持多文件合并提交，应将同一轮敲定内容合并成一个 commit。
2. 如果当前工具只能单文件提交：
   - 单文件变更可以直接提交。
   - 多文件变更不要拆成多个 commit 硬提交；先生成待提交清单、补丁或文件包，等待可合并提交的环境执行。
3. 多文件提交完成后，应回读 commit 或文件内容，确认提交范围符合本轮讨论。

## 隐私与边界

默认不得写入 GitHub 或 Drive 的内容包括：

- 个人健康、用药、家庭、工作、账号、财务、联系人、现实身份信息。
- 明确标记为私密、敏感、备忘、仅自己看的材料。
- 与项目创作无关、且没有被用户单独授权沉淀的生活记录。

如用户确实要求保存这类内容，必须确认具体文件或具体类别，并说明保存位置与可见范围。

## GitHub 与 Drive 的关系

1. GitHub 是版本主库，负责保存正式静态资料、提交历史和可回滚版本。
2. Drive 是读取镜像和跨模型入口，便于没有 GitHub 工具的模型访问。
3. GitHub 更新后，如 Drive 仍用于模型入口，应在需要时同步更新 Drive 的入口索引或对应镜像文件。
4. 不得把“Drive 已同步”说成“GitHub 已提交”；两者必须分别验证。

## 交付时的报告格式

完成更新后，回复应包括：

- 更新了哪些文件。
- commit SHA 或链接。
- 是否回读验证成功。
- 如 Drive 也同步了，说明同步文件和验证结果。
- 如未能提交或同步，明确说明原因和下一步需要用户做什么。
