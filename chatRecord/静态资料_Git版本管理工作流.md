# 静态资料 Git 版本管理工作流

本文记录“磕”项目静态资料的长期维护方式。内容写成通用模型指令，不依赖某一个具体模型或产品；任何支持自定义 instructions、能访问 GitHub 或本地 git 仓库的模型，都应按此执行。

## 资料源优先级

1. GitHub 仓库是静态资料的唯一日常维护源。
   - 仓库：`laippmiles/ke-project`
   - 主分支：`main`
   - 二创资料目录：仓库根目录下的 `00_入口与规章`、`01_核心总集`、`02_原作对白与校准`、`03_创作稿件`、`04_提示词与外部工具`、`05_素材附件`、`90_旧版与待核对`。
   - 非二创讨论记录目录：`chatRecord/`
   - 同步脚本和维护工具目录：`_system/`
2. 原 Google Drive 和 ChatGPT Library 文件只作为迁移历史背景。除非用户明确要求回查旧版，不作为日常维护源。

## 日常读取规则

1. 需要读取项目静态资料时，读取 GitHub 仓库中的对应文件。
2. 先读 `00_入口与规章/磕_GitHub_入口索引.md`，再按索引进入具体文件。
3. 无法访问指定 GitHub 文件时，必须明确说明缺失，不能凭记忆补设定，也不能编造原作对白或项目规则。
4. 不再默认回退到 Drive 或 Library；除非用户明确要求回查旧版。

## 写入与提交规则

1. 讨论过程中不要立即提交。先记录待更新内容，等待用户明确表示“敲定”“归档”“提交”“按这个改”等确认。
2. 用户确认后，再更新静态资料。
3. 一轮讨论敲定的结果必须尽量合并为一个 commit。
4. commit message 应简短说明本轮沉淀内容，例如：
   - `更新项目资料维护规则`
   - `归档杀铃关系阶段设定`
   - `记录 Git 工作流`
5. 提交前必须检查变更边界：
   - 二创世界观、人物、对白、正文资料写入根目录下对应的二创资料目录。
   - 与二创无关的流程、工具、插件、故障排查、工作流结论写入 `chatRecord/`。
   - 同步脚本和维护工具写入 `_system/`；普通写作资料不要放入 `_system/`。
   - 私密、敏感、个人资料不得默认写入仓库。

## 多文件变更规则

1. 如果当前工具支持多文件合并提交，应将同一轮敲定内容合并成一个 commit。
2. 如果当前工具只能单文件提交：
   - 单文件变更可以直接提交。
   - 多文件变更不要拆成多个 commit 硬提交；先生成待提交清单、补丁或文件包，等待可合并提交的环境执行。
3. 多文件提交完成后，应回读 commit 或文件内容，确认提交范围符合本轮讨论。

## 隐私与边界

默认不得写入 GitHub 的内容包括：

- 个人健康、用药、家庭、工作、账号、财务、联系人、现实身份信息。
- 明确标记为私密、敏感、备忘、仅自己看的材料。
- 与项目创作无关、且没有被用户单独授权沉淀的生活记录。

如用户确实要求保存这类内容，必须确认具体文件或具体类别，并说明保存位置与可见范围。

## 目录结构变更记录

## 交付时的报告格式

完成更新后，回复应包括：

- 更新了哪些文件。
- commit SHA 或链接。
- 是否回读验证成功。
- 如未能提交，明确说明原因和下一步需要用户做什么。
